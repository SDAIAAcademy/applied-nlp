Transfer learning

Why a few thousand examples are enough

Pretraining (someone else's GPUs)
billions of tokens → grammar, semantics, world knowledge, Arabic morphology
↓ reuse the weights
Fine-tuning (your GPU, minutes)
3k labelled tickets → "which of 27 intents?"
  • The body already produces useful representations. Fine-tuning nudges them toward your labels.
  • Small learning rate (≈2e-5) so you don't erase pretraining.
  • The new head starts random. It's the only part learned from scratch.
Decision

When should you fine-tune?

Good reasons

  • A fixed task with a stable label set and labelled data
  • High volume: need low latency and cost per request
  • Consistent output format or style a prompt can't enforce
  • Domain language the base model handles poorly
  • Distill an expensive LLM into a small model

Poor reasons

  • Teaching facts that change (prices, policies). Use RAG.
  • No evaluation set, so you can't tell if it helped
  • A few dozen examples. Try few-shot first.
  • "Because everyone fine-tunes"
Rule of thumb: fine-tuning teaches behaviour (how to respond). RAG supplies knowledge (what is true now). Many production systems use both.
Data is the model

Label quality beats label quantity

Guidelines

Write a definition and 2 examples per label, including how to break ties (get_refund vs. track_refund).

Agreement

Have two people label the same 100 tickets. If they agree < 85%, fix the guidelines before training.

Coverage

Every label, every language and dialect, short and long, polite and angry, typos.

How many? For an encoder classifier, start with ~50–100 per class, measure, then add data where the confusion matrix says it's needed.
Label noise sets a ceiling. A model can't beat the consistency of its labels.
Splits and leakage

Your test score is only as honest as your split

  • Train to fit · validation to choose (epochs, thresholds, models) · test once, at the end.
  • Stratify by label so rare intents appear in every split.
  • Near-duplicates across splits inflate scores. Templated datasets (like ours!) are full of them.
  • Group by customer / thread / template so related items stay on one side.
Train: "I need help to cancel order {{Order Number}}"
Test: "I need help canceling order {{Order Number}}"
→ The model memorized, it didn't generalize.
Check: embed train and test; flag test items with cosine > 0.95 to any train item. Report scores with and without them.

Hugging Face Datasets

From a DataFrame to model-ready tensors

from datasets import Dataset, DatasetDict
from transformers import AutoTokenizer, DataCollatorWithPadding

labels = sorted(train_df.intent.unique())
label2id = {l: i for i, l in enumerate(labels)}
id2label = {i: l for l, i in label2id.items()}

def to_ds(df):
    return Dataset.from_pandas(
        df.assign(label=df.intent.map(label2id))[["text", "label"]],
        preserve_index=False)

ds = DatasetDict(train=to_ds(train_df), validation=to_ds(val_df),
                 test=to_ds(test_df))

tok = AutoTokenizer.from_pretrained("distilbert/distilbert-base-multilingual-cased")
ds = ds.map(lambda b: tok(b["text"], truncation=True, max_length=32),
            batched=True)
collator = DataCollatorWithPadding(tok)   # pads per batch, not globally
Dynamic padding: pad each batch to its longest item. It's often 2–4× faster than padding everything to 512.
max_length from your data: the 99th percentile of token lengths (Lab 1.1).
Save the label maps with the model. Shuffled label IDs are a classic silent production bug.

Architecture

Encoder + a tiny head

Ticket tokens[CLS] my refund …
→
Pretrained encoder6–12 layers, updated with small LR
→
[CLS] / pooled vector768-d
→
Headdropout → Linear(768 → 27)
→
Logits → softmaxp(intent)

Cross-entropy loss for one example with true class y:

L = −log p(y | ticket)

p = 0.9 → L = 0.11 · p = 0.1 → L = 2.3. Confident mistakes are punished hard.

Difference from Day 1: there, the encoder was frozen and only logistic regression learned. Here, gradients flow into the encoder too, so the representations themselves adapt to your labels.

Code

The Trainer recipe

from transformers import (AutoModelForSequenceClassification, TrainingArguments,
                          Trainer, EarlyStoppingCallback)

model = AutoModelForSequenceClassification.from_pretrained(
    "distilbert/distilbert-base-multilingual-cased", num_labels=len(labels), id2label=id2label, label2id=label2id)

def compute_metrics(p):   # sklearn f1_score on argmax of logits
    return {"macro_f1": f1_score(p.label_ids, p.predictions.argmax(-1), average="macro")}

args = TrainingArguments(
    output_dir="runs/intent", learning_rate=3e-5, num_train_epochs=4, warmup_steps=0.1,
    per_device_train_batch_size=32, weight_decay=0.01, seed=42,
    fp16=torch.cuda.is_available(),          # warmup_steps < 1 = ratio of total steps
    eval_strategy="epoch", save_strategy="epoch", save_total_limit=1,
    load_best_model_at_end=True, metric_for_best_model="macro_f1", report_to="none")

trainer = Trainer(model=model, args=args, train_dataset=ds["train"], eval_dataset=ds["validation"],
                  processing_class=tok, data_collator=collator, compute_metrics=compute_metrics,
                  callbacks=[EarlyStoppingCallback(early_stopping_patience=2)])
trainer.train()
trainer.evaluate(ds["test"])        # once, at the very end
Learning curves

Read the curves before you read the score

  • Both falling: still learning, maybe train longer.
  • Train ↓, val ↑: overfitting, so stop early and keep the best checkpoint.
  • Both flat and high: LR too low/high, a bug, or labels too noisy.
  • Val loss ↑ but F1 still ↑: happens (over-confidence). Select by your target metric.

The memory wall

Full fine-tuning needs ~16 bytes per parameter

Per parameter (mixed precision + Adam)Bytes
Weights (bf16) + fp32 master copy2 + 4
Gradients2–4
Adam moments (m, v) in fp328
Total (before activations)≈ 16
24 GB
to fully fine-tune a 1.5B model
~112 GB
for a 7B model: multiple GPUs
LoRA

Freeze W. Learn a low-rank update ΔW = B·A

  • Trainable params per matrix: r(d + k) = 16 × 8192 ≈ 131k instead of 16.8M (0.8%).
  • Optimizer state only for adapters, so memory drops dramatically.
  • B starts at zero, so training starts exactly from the base model.
  • Adapters are small files (tens of MB). Swap them per task on one base model.
QLoRA: load the frozen base in 4-bit (NF4) and train bf16 adapters on top. A 7B model fits on one 16–24 GB GPU.

SFT data

Supervised fine-tuning data = conversations you want to see

{"messages": [
  {"role": "system",
   "content": "Classify the support ticket. Reply with JSON."},
  {"role": "user",
   "content": "i was charged 2 times for order A-55821!!"},
  {"role": "assistant",
   "content": "{\"intent\": \"payment_issue\", \"category\": \"PAYMENT\", \"priority\": \"urgent\"}"}
]}
Train with the same chat template and system prompt you'll use at inference.
Consistency > volume: 1–3k clean, uniform examples teach a format well.
Distillation: you can generate targets with a big model, but then review them. You inherit its errors.
Loss masking

Learn to answer, not to repeat the question

<|im_start|>system …<|im_start|>useri was charged 2 times …<|im_start|>assistant {"intent":"payment_issue",…}<|im_end|>
Prompt tokens (grey): label = -100, ignored by the loss.
Assistant tokens (green): label = token ID, so they're trained on.
prompt_ids = tok.apply_chat_template(msgs[:-1], add_generation_prompt=True)["input_ids"]
full_ids   = tok.apply_chat_template(msgs)["input_ids"]
labels     = [-100] * len(prompt_ids) + full_ids[len(prompt_ids):]
TRL's SFTTrainer does this for you (assistant-only loss). We do it by hand in the lab so it's not magic.

Error analysis

Read the errors. Then decide what to do.

  1. Confusion matrix → top 3 confused pairs
  2. Read 20 errors (yes, actually read them)
  3. Tag each one with a cause:
CauseAction
Label noise / wrong gold labelFix data, re-evaluate
Genuinely ambiguous ticketMerge labels or allow multi-label / abstain
Missing coverage (dialect, typo)Collect / augment that slice
Real model errorBigger model, more data, better features
Out of scopeAdd an "other" class + threshold
Robustness

Behavioural tests: unit tests for models

Invariance

Changes that shouldn't change the label: names, order numbers, typos, polite ↔ rude, EN ↔ AR.

Directional

Changes that should move the output: add "URGENT, charged twice" → priority must not go down.

Minimum functionality

Short, obvious cases every model must pass: "cancel my order" → cancel_order.

def test_invariance_order_number(predict):
    a = predict("I want to cancel order A-10001")
    b = predict("I want to cancel order Z-99231")
    assert a == b == "cancel_order"
Inference engineering

Make it fast and cheap before you make it bigger

  • Batch requests; sort by length to minimize padding.
  • Truncate to the p99 length (~24 tokens for our tickets).
  • fp16 on GPU; dynamic int8 quantization or ONNX Runtime on CPU.
  • Distill: a 6-layer model is often within a point of a 12-layer one.
  • Load the model once per process, not per request.
import torch
from transformers import pipeline

clf = pipeline("text-classification",
               model="artifacts/intent-distilmbert",
               device=0 if torch.cuda.is_available() else -1,
               truncation=True, max_length=32)

clf(["where is my refund", "وين طلبي"], batch_size=64)
