BPE

Starts from characters or bytes and merges the most frequent pairs. Used by GPT, Llama, Qwen and most LLMs.

WordPiece

Like BPE, but merges by likelihood. Continuation pieces start with ##. Used by BERT and AraBERT.

Unigram (SentencePiece)

Prunes a large vocabulary probabilistically and treats spaces as ▁. Used by T5, XLM-R and mT5.

BPE in 60 seconds

Learn merges from a corpus, then apply them in order

StepMost frequent pairCorpus after merge
0–l o w · l o w e r · n e w e s t

Key insight: the vocabulary reflects the training corpus. A tokenizer trained mostly on English has few Arabic merges.
Byte-level BPE starts from the 256 bytes, so nothing is ever unknown. But an Arabic letter takes 2 bytes in UTF-8, so Arabic can blow up to many tokens per word.
Same text, different tokenizers

Each model family has its own conventions

WordPiece (BERT): continuation pieces start with ##

[CLS]token##izationisfun[SEP]

Byte-level BPE (GPT-2, Qwen): a leading space is part of the token, shown as Ġ

SentencePiece Unigram (XLM-R): word starts are marked with ▁

Rule #1: always use the tokenizer that ships with the model. A model fed IDs from another vocabulary sees garbage.

A metric you should track

Fertility: tokens per word

Fertility = n_tokens / n_words. Lower is usually better: cheaper, faster, more text fits in context.

  • English-centric byte-level tokenizers can produce several times more tokens for Arabic than for English.
  • Multilingual (XLM-R, Qwen) and Arabic-specific (AraBERT, Jais, ALLaM) tokenizers close the gap.
  • Same message → different bill and different context budget.

Engineering checklist

Tokenization mistakes that reach production

  • Mixing a model with another model's tokenizer
  • Truncating the important part (e.g., the actual question at the end of a long email)
  • Estimating cost with word counts instead of token counts
  • Over-normalizing input to an LLM (removing diacritics or casing it relies on)
  • Forgetting the chat template for instruction models (Day 2)
  • Losing character offsets needed to highlight extracted spans
  • Assuming the context limit applies only to input. Output tokens count too.
  • Not testing on dialect, typos, emoji and code-switched text

02
From IDs to vectors

An embedding is a learned coordinate

  • A token ID indexes a row of an embedding matrix (vocab × d, e.g., 250k × 384).
  • Training pushes rows so that things used similarly end up close.
  • Transformers then make vectors contextual: the same token gets different vectors in different sentences.
  • A sentence embedding compresses a whole text into one vector, which is ideal for search and clustering.
2-D projection for intuition. Real embeddings have 384 to 1024+ dimensions.
Similarity

Cosine similarity: compare directions, not lengths

cos(a, b) = a·b / (‖a‖‖b‖)

  • Range −1 … 1. In practice most text pairs fall between 0 and 1.
  • Normalize once (‖v‖ = 1) and cosine becomes a plain dot product, so a matrix multiply ranks the whole corpus.
  • Scores are relative. A 0.82 means nothing across models; compare rankings, not raw values.
import numpy as np

def cosine(a, b):
    return a @ b / (np.linalg.norm(a) * np.linalg.norm(b))

# normalized matrices: one matmul ranks everything
E = corpus_emb / np.linalg.norm(corpus_emb, axis=1, keepdims=True)
q = query_emb / np.linalg.norm(query_emb)
scores = E @ q                    # shape: (n_docs,)
top5 = np.argsort(-scores)[:5]

Why not just average a raw BERT?

You can, but it's mediocre. Sentence-embedding models are further trained with contrastive pairs (question ↔ answer, paraphrases), so similar meanings are pulled together and the rest pushed apart.

Bi-encoder vs. cross-encoder

Bi-encoder: embed each text separately. Fast, indexable, used for retrieval.
Cross-encoder: read both texts together. Accurate, slow, used for reranking the top-k (Day 2).

Code

Semantic search in ~15 lines

from sentence_transformers import SentenceTransformer
import faiss

model = SentenceTransformer("intfloat/multilingual-e5-small")

docs = history["text"].tolist()
doc_emb = model.encode([f"passage: {d}" for d in docs],
                       normalize_embeddings=True, batch_size=64, show_progress_bar=True)

index = faiss.IndexFlatIP(doc_emb.shape[1])      # inner product == cosine (normalized)
index.add(doc_emb)

def search(query, k=5):
    q = model.encode([f"query: {query}"], normalize_embeddings=True)
    scores, ids = index.search(q, k)
    return history.iloc[ids[0]].assign(score=scores[0])

search("لم يصلني المبلغ المسترد")   # Arabic query, English history
Point out that the Arabic query retrieves English tickets: multilingual models share one vector space across languages. That's cross-lingual retrieval for free, but it's also something to evaluate rather than assume.
Evaluation

Is the search any good? Measure it.

MetricQuestion it answers
Recall@k / Hit@kIs a relevant result anywhere in the top k?
Precision@kWhat fraction of the top k is relevant?
MRRHow high is the first relevant result? (1/rank)
nDCG@kGraded relevance with position discount
Cheap relevance labels: in our data, a retrieved ticket with the same intent as the query counts as relevant. You get an eval set for free.
Better: 50–100 real queries with hand-judged relevant documents. Small, but it's ground truth.
Leakage: the query must not be in the index. Search with test tickets against train tickets.
Failure modes

Where pure semantic search fails

  • Exact identifiers: order #A-55821, product codes, IBANs. Embeddings blur these, so add keyword search (BM25) and combine → hybrid.
  • Negation: "I don't want a refund" sits close to "I want a refund".
  • Length mismatch: a 5-word query vs. a 2-page document; chunk the documents (Day 2).
  • Domain jargon the model never saw → evaluate, then consider fine-tuning embeddings.
  • Cross-lingual gaps: dialect queries against MSA or English documents. Test them explicitly.
  • Stale index: new policies never re-embedded.

03
The problem attention solves

Meaning depends on context

"You charged me twice for one order"

→ billing, PAYMENT

"My phone won't charge since the update"

→ technical issue

  • A static embedding gives "charge" one vector, a blend of both meanings.
  • A transformer lets each token look at every other token and update its vector, so "charge" near "twice" and "order" becomes billing-flavoured.
In the lab you'll extract the contextual vector of the same word in two sentences and watch their cosine similarity drop.
Self-attention

Every token asks, advertises and shares

Query (Q): "what am I looking for?"
Key (K): "what do I contain?"
Value (V): "what I pass on if you attend to me"

Attention(Q,K,V) = softmax(QKᵀ/√d)·V

  1. Project each token vector into Q, K, V (learned matrices).
  2. Score every pair: q_i · k_j, scaled by √d.
  3. Softmax each row into weights that sum to 1.
  4. New vector = weighted sum of values.
Cost grows with n² in sequence length, which is why context windows are limited and long contexts are expensive.
Seeing it

An attention map (one head, one layer)

  • "charged" puts weight on "order" and "twice": evidence for the billing sense.
  • Multi-head: 12+ heads per layer each learn different patterns (syntax, coreference, position…).
  • Many layers (6–80+) stack these updates.
Caution: attention weights are a diagnostic, not an explanation of the decision.
The block

A transformer is the same block, stacked

Token embeddings + positional information
↓
× N layers
Multi-head self-attention → add & normalize
↓
Feed-forward network (per token) → add & normalize
↓
Head (task-specific): classify · predict mask · next token
Positions: attention is order-blind, so position must be injected. Older models use learned absolute positions; modern LLMs use RoPE (rotary), which extends better to long contexts.
Residual + norm: lets very deep stacks train stably.
The head is small. Pretraining learns the body, and your task usually only needs a new head (Day 3).

Zero-shot classification

Reuse a model trained for "does A imply B?"

An NLI model scores whether a premise entails a hypothesis. Turn each label into a hypothesis:

Premise: "I was billed twice for the same order"
Hypothesis: "This customer message is about payment."
  • No training data needed; labels can change at runtime.
  • Label wording matters a lot: "billing problem" ≠ "PAYMENT".
  • Cost scales with the number of labels (one pass per label).

clf = pipeline(
    "zero-shot-classification",

)

The best value-for-effort classifier

from sentence_transformers import SentenceTransformer
from sklearn.linear_model import LogisticRegression

enc = SentenceTransformer("intfloat/multilingual-e5-small")

Evaluation

Accuracy is not enough

MetricMeaning for "complaint" class
PrecisionOf tickets we flagged as complaint, how many were?
RecallOf real complaints, how many did we catch?
F1Harmonic mean of the two
Macro-F1Average over classes: rare classes count equally
Weighted-F1Average weighted by class frequency
Imbalance trap: if 95% of tickets are "other", a model that always says "other" has 95% accuracy and zero use.
Confusion matrix shows which classes get mixed up (e.g., get_refund vs track_refund). That's where you focus labelling and fixes.
Slice it: report English vs. Arabic, short vs. long, dialect vs. MSA.
Thresholds and abstention

Let the model say "I'm not sure"

Raising the threshold improves accuracy on what you keep, but more goes to humans.
def route(text, tau=0.6):
    p = clf.predict_proba(embed([text]))[0]
    i = p.argmax()
    if p[i] < tau:
        return {"intent": None, "action": "human_review"}
    return {"intent": clf.classes_[i], "conf": float(p[i])}
  • Pick τ from validation data, not test.
  • Thresholds can be per class: stricter for costly errors.
  • Raw probabilities are often over-confident. Calibrate if the score drives decisions.
Think like the business

Not all errors cost the same

Missed urgent complaint

Customer churns, social-media escalation. High cost, so optimize recall for complaint and payment_issue.

Wrong queue

An agent re-routes it, costing minutes. Medium cost.
